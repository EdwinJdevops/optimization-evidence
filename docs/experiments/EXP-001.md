# EXP-001: Capacity reduction versus realized cash savings

Status: planned

## Objective

Prove that the system distinguishes two superficially similar optimization changes:

- Arm A: application resource requests are reduced, service remains healthy, but billable node capacity does not decrease. Expected terminal outcome: `NO_CASH_SAVING`.
- Arm B: application resource requests are reduced, service remains healthy, and a cluster autoscaler removes a billable EC2 worker. Billing evidence later confirms the capacity change. Expected path: `CAPACITY_REALIZED -> BILL_OBSERVED -> ATTRIBUTION_VERIFIED -> REALIZED` if attribution checks pass.

The experiment is falsified if the evidence model cannot distinguish these cases without manual interpretation.

## Spend guardrail

An AWS Budget named `optimization-evidence-exp-001` is configured at USD 20/month and excludes credits/refunds from masking gross consumption. Actual target spend for the experiment is materially below the budget; the budget is a guardrail, not a target.

## Environment requirements

- dedicated short-lived EKS cluster; do not reuse unrelated clusters;
- no NAT Gateway unless an experiment requirement proves it necessary;
- two low-cost EC2 worker nodes initially, with autoscaler minimum 1 and maximum 2;
- no SSH ingress;
- all resources tagged `Project=optimization-evidence`, `Experiment=EXP-001`, `Environment=research`;
- deterministic teardown script/IaC;
- constant synthetic application traffic and recorded workload demand;
- Prometheus-compatible operational evidence;
- Git commit/manifest digest recorded as the change identity.

## Arm A

1. Establish stable baseline demand and health.
2. Record initial requests, node set, instance IDs, and billing observation window.
3. Reduce workload requests enough to release schedulable capacity but intentionally prevent node removal.
4. Verify workload health for the defined observation window.
5. Confirm node/instance set is unchanged.
6. Classify `NO_CASH_SAVING`; do not wait for a fictional billing delta.

## Arm B

1. Restore/re-establish the controlled baseline.
2. Permit autoscaler scale-down from two nodes to one.
3. Apply a request reduction that allows all target pods to fit safely on one worker.
4. Verify workload health.
5. Record Kubernetes node deletion and matching EC2 instance termination.
6. Wait for CUR 2.0 evidence covering the relevant hours.
7. Compare resource-level usage/cost evidence, accounting for pricing/commitment fields available in CUR.
8. Normalize against demand and reject attribution if unrelated changes materially confound the window.
9. Only then permit `ATTRIBUTION_VERIFIED -> REALIZED`.

## Required artifacts

- exact manifests and Git SHAs;
- pre/post workload resource configuration;
- timestamps in UTC;
- pod/node/instance identity mapping;
- operational metric snapshots;
- autoscaler events;
- EC2 lifecycle evidence;
- relevant raw CUR records and deterministic derived calculation;
- final outcome and any uncertainty.

## Stop conditions

Stop immediately on unexpected spend acceleration, unexplained infrastructure mutation, operational instability outside the synthetic workload, or inability to identify the exact resources involved.
